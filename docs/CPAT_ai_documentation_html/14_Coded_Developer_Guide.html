Project structure

Folders located in the root directory:

├── data
├── cpat_documentation
├── cpat_model
├── cpat_shiny
├── cpat_testing

Files contained in the root folder are: - run_model.py - entry point for running model without the Shiny application - config.py - used to define scenarios for run_model.py and contain DATA_PATH for the input data. The keys in CONFIG define the scenario names, and the values define the DashboardInputs that overwrite the default inputs for each scenario. Also holds DATA_PATH for the input data. - app.py - servs as the main entry point to the Shiny application - environment.yml - Defines the Conda environment, including the Python version and all core dependencies installed via Conda (e.g. pandas, numpy, pyarrow, matplotlib) - requirements.txt - lists runtime Python packages installed via pip that are not handled by Conda - dev-requirements.txt - lists additional development dependencies (e.g. testing tools) and extends requirements.txt

Environment setup

This project uses Conda for environment management. The instructions below show an example of how to set up the environment using Conda and the provided environment.yml file.

Create the Conda environment from the project root:

conda env create -f environment.yml

Activate it:

conda activate cpat_p

Install development dependencies (optional, for developers):

pip install -r dev-requirements.txt

To update an existing environment:

conda env update -f environment.yml --prune
pip install -r dev-requirements.txt --upgrade

Data structure

Data handled in the model uses the pd.DataFrame type (or pd.Sereis), typically indexed with 3 main index levels defined as ID_COL_NAMES = ['CountryCode', 'SectorCode', 'FuelCode']. Not all data require all three index levels; when a level is redundant or not optimal for calculations. For time series data frames - columns representing years are stored as strings, e.g. '2025'.

Index and columns of the data are marked at the bottom of docstrings each dosctring as “(index), columns”, eg (c, s), 'Scenario', <simulation_years[0] - 1, simulation_years[1]>, meaning it has MultiIndex with 2 index levels 'CountryCode' and 'SectorCode', 1 column named Scenario and rest of the columns representing time series for years in range of <simulation_years[0] - 1, simulation_years[1]>. In index description c relates to CountryCode, s to SectorCode and f to FuelCode.

cpat_documentation

In cpat_documentation/user there are .md files that are used in the application documentation section. Their content is read and embedded in: cpat_shiny\ui\sections\documentation_section.py.

cpat_documentation/developer contains developer documentation.

cpat_model

This folder contains all the logic used for running the model and processing the results. (TODO: elaborate when WiP code is finished.)

Path Contents
mitigation/ The mitigation module: GDP, policies, carbon pricing, emission factors, elasticities, prices, energy consumption, emissions, power, CH4, GHGs, methane fee, fiscal revenues, aggregations
distribution/ The household distribution (incidence) module: one file per step group of the pseudocode (other/more/CPAT_Distribution_Module_Pseudocode.docx): data.py (loaders), price_changes.py (step 1), budget_shares.py (2-3), effects.py (4-6), rebasing.py (7), recycling.py (8), welfare.py (9-12), sectoral.py (13), distribution.py (14, the Distribution class)
data_read/input_data.py InputData: every data table, mitigation and distribution (distn_*)
dashboard_inputs.py, distribution_inputs.py Default inputs of the mitigation module and of the distribution module (the Excel Distribution sheet has its own input block)
scenario_results.py ScenarioResults: one finished scenario run, so Distribution can compare a policy scenario with the baseline
indicators/ Result indicators and their Excel export
constants.py Codes shared with the Excel models (distribution codes at the end; note: hea is heat in mitigation and health services in distribution)

Distribution in run_model.py. After all scenarios have run, run_distribution takes the baseline scenario (scenario_type == c.BASELINE) and, for every policy scenario and every selected country with household survey data (Egypt so far), derives the direct price change by fuel (residential retail prices; oil products their all-sector price; electricity the power model’s price, power.demand.rp_demand, which covers the projected years) and the carbon-pricing revenue, and builds a Distribution for the analysis year (DistributionInputs, default the last simulated year). run_model() returns (scenario_results, distributions).

cpat_shiny

Folder containing Shiny logic. Server and UI are further divided into server_logic and ui folders.

Server

../server_logic/reactive/ stores definitions and handlers for reactive values that are used to hold the state of different sections while navigating through the application.
Globally relevant reactive values (eg results) are defined in ../server_logic/server.py.

../server_logic/visualization/ contains all the logic for graph generation.
There are 2 types of graphs implemented for visuzlization. Graph class implements plotly graphs (embedded in Visualization section), whereas GraphXL class Matplotlib graphs (used in indicators.xlsx result file). The only reason of using 2 separates libs is because shinyapps.io does not provide kaleido nor orca for static image export from plotly graphs.
Graphs generation takes place in GraphGenerator class where depending on user selection different graph processors are called. These processors are ECGraphs, EMGraphs and PGraphs, all of them extend from a generic GraphProcessor.

Rest of the files in ../server_logic/ are the main ../server_logic/server.py file and handlers further used in the server.py file.

UI

In ../ui/components/common/ shared components are located. Shared components are or potentially can be reused in various sections of the application.

../ui/css/head.py contains global styles included in head content.

../ui/sections/ hold UI for all the sections availble in the sections selector Section is selected based on the selector state: ../ui/sections/section_selection.py

../ui/labels.py stores all the UI labels/text so it can be reused in all the application.

Validation

../validation/ includes UI validation logic for user input. It is created in a custom way as at the time of creating the application Python Shiny did not provide any validation logic.

Mapping

.../mapping.py holds all the mappings that are used in UI components. Some mappings are provided from an Excel file .../mappings.xlxs, that are loaded in .../mapping.py

cpat_testing

Contains unit tests for the new logic. cpat_testing should follow the project structure. cpat_testing/model folder holds unit tests covering functions from cpat_model. Folders inside cpat_testing/model are organised consistant to the cpat_model directory.

Some unit tests from cpat_testing/model read expected data frames from .csv files located in cpat_model/model/data_expected. Remeber to update share drive files after changing/creating tests that load expected data frames.

pytest: Please name test files test_{tested_file}.py and try to define test functions names so they indicate what they check, eg: def test_{tested_function}(...): or def test_{tested_functionality}(...):. Please mind that by default, pytest looks for files that match the pattern test_*.py or *_test.py, as well as test functions that start with test_.

../conftest.py holds configuration for all cpat_testing dir. Used to ensure that the root directory is always added to the Python path whenever pytest is ran. We could also hold here fixtures used accross multiple files.

For running all tests:

pytest cpat_testing

For running tests only in a given dir, eg in model:

pytest cpat_testing/model

For running just 1 test:

pytest -k "test_my_func"

Adding -s (pytest -s -k "test_my_func") disables output capturing, allowing print statements to appear in the terminal. (for test debugging)

Data folder structure and data reading

All the data used in the model resides in data/ folder that has the following structure:

├── data
│   ├── dummy

The distribution tables (data/dummy/distn_*.csv, Egypt household survey, IO_GTAP, HH_Elast, ASPIRE, WHO cooking, GDP ratios, mappings) are real data exported from data/distribution/data_standardized/CPAT_DistributionalData.xlsx by excel_ai/distribution/scripts/build_distribution_model_data.py (rerun it after changing that workbook; it writes to data/dummy/, or to a folder given as its argument, e.g. REAL_DATA_PATH).

The target format for data files is .pkl.bz2. Currently, many data input files are still stored as .csv in data/dummy/, but these are temporary and will be migrated to .pkl.bz2 format.

Input data loading is handled in cpat_model\data_read\input_data.py. All functions that are used to load the data should have [Data Loading] tag in their docstring.

Running the model

Shiny application is not updated to recent changes and the only way to run the model now is by running python run_model.py. The pinned stack is Python 3.12, pandas 2.2.3, numpy 2.2.0 (environment.yml); the model and the tests also run with pandas 3.x (copy-on-write: write through .iloc/.loc, never into .values).

run_model.py

Dashboard inputs (manual inputs) can be adjusted in config.py file by modifying SCENARIOS. Each key, value pair in SCENARIOS dictionary represents name of a scenario and parameters that overwrite the default dashboard input values for this specific scenario.

Parameters that can be adjusted from the code are: selected_countries and last_simulation_year. Please do not change base_year = 2022.

Saving the results is not handled by run_model.py and can be easily implemented in a custom way by identifying the scenario via the keys in config.SCENARIOS and saving the desired variables or tables to CSV/XLSX files.

Running Shiny app localy

Run from the project root:

python -m shiny run app.py

Tip: flag --reload automatically reloads the app when the code is eddited.

By default the app can be accessed on:

http://127.0.0.1:8000/
