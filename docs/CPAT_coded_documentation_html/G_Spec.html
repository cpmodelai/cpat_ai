1. The request (user, 2026-10-29), cleaned up

1.1 Goal

Build the full Python model (“Coded CPAT”) that directly replicates the mitigation and distribution modules of Excel-AI (excel_ai/CPAT-AI-Mitigation-Prototype_v<version>.xlsm, CPAT-AI-Distribution-Prototype_v<version>.xlsm). The numbers must match Excel-AI. The overall norm is: always follow Excel-AI. Where an Excel-AI choice looks strange or wrong, report it to the user rather than silently departing; known departures from legacy CPAT are already tracked in the register (bugs L, issues I, departures LD, upgrades U).

The purpose of the code is full human readability: a reader with the methodology in one hand should be able to find each equation in the code in the other.

1.2 Ways the model is run

  1. From saved scenarios: a table of scenario inputs in the MTInputs form (one row per NameOfParameter, one column per scenario), as legacy CPAT and Excel-AI ScenarioDefinition.
  2. From a reactive Shiny user interface (later), which populates the same inputs dynamically.
  3. Both use an advanced inputs file as well: time series and longer-form inputs of different types (the legacy Manual inputs tab).

The code runs many countries and many scenarios in one call (batch, comparisons), and one country with two or more scenarios (the main user interface).

1.3 Data: databases

Python and Excel-AI both run from the same databases. A database holds two or more complete sets of data:

Set Contents Where
Full Every table, including the four proprietary tables A separate, private repository (never this one)
Public Every table except the four proprietary tables: energy balances (EnergyCons/Balances), domestic prices (Prices_dom), the GTAP input-output table (IO_GTAP) and the household survey (HHSurvey) This repository (data/)

This mirrors how Excel-AI and legacy CPAT work (legacy NoPropData workbooks lack the same four tables).

1.4 Testing

  • Compare Python with Excel-AI systematically.
  • Compare Python or Excel-AI with legacy CPAT.
  • In each case first for one country, then for all.
  • For these comparisons use a systematic dataset: the public set (full except the four proprietary tables), with the four tables filled the same way in every model.

1.5 Documentation and readability

  • The methodology is in docs/01_MainDocumentation/*.qmd. A website will be built from qmd (to HTML), with tabs for Excel-AI and for Python.
  • Plan the Python project in a human-readable way too, in qmd (markdown with extras) that can be built into the website and into Word.
  • An equation list: an executive summary with the core equations of each part, and appendices with all the adjustments. It uses the Greek letters and index letters of the methodology documentation; indices are shown only where they add clarity (otherwise the text says which indices an equation ranges over).
  • A parallel version with code names instead of Greek letters, using the authoritative list of CPAT variable codes (e.g. ener), the codes map in excel_ai/.
  • Box diagrams of the modular structure.
  • A separate NORMS and TODO for the Python project. Most Excel norms (formatting) do not apply; the overriding norm is to follow Excel-AI.

1.6 Structure

  • Decide up front whether the model computes everything for year t (all modules, including air pollution and transport co-benefits) before moving to year t+1.
  • Placeholder modules for air pollution and transport co-benefits, with their imports and exports defined now. Transport co-benefits will later be related to the transport (engineer) mitigation model.
  • Switchable core equations. The structure must allow later switching between forms of the core equations through one global switch: simple-CPAT (basic CPAT equations for every sector, power included), standard-CPAT (engineering power and transport models on), CPAT partial adjustment, CES partial adjustment (taking the CES-compatible price of the energy service), and CDPM (SISEPUEDE) plus FTT-like. Excel-AI implements its core equations as LAMBDA formulas; the Python forms play the same role. Only the Excel-AI form is built now.
  • Keep the existing, clean folder structure of coded/ as the starting point; do not clutter the core folders with working files; prefer a subfolder (with one pointer file at the top) over more than three new files in a folder. Recommend improvements to the structure, then make them.

1.7 Sequence of work

  1. Plan the folder and code structure for readability (this document, NORMS.md, the diagrams).
  2. The equation list (Greek letters) and its parallel version with code names.
  3. Design choices: documented here (section 10) and gone through with the user, question by question.
  4. The detailed plan (section 11 and coded/TODO.md), then the build.

2. Principles

  1. Follow Excel-AI. The numbers of Coded CPAT equal Excel-AI’s, code by code, year by year; a difference is a defect of one of the two, found and registered. Through Excel-AI, Coded CPAT inherits the replication rule (never replicate a legacy bug; replicate and track every legacy issue).
  2. Readable first. One equation, one function, with the equation in the docstring as in the equation list; names from the codes map; no hidden constants; the model order written once (mitigation/chain.py). Speed comes second, and is reached by working on whole arrays of countries and scenarios at once, not by obscure code.
  3. One model, many front ends. One entry point, cpat_model.run(scenarios, database, settings), used by the command line (scenario files, many countries and scenarios), the Shiny app (one country, two or more scenarios, reactive) and the tests.
  4. Same inputs, same data, same codes as Excel-AI. Scenario inputs are MTInputs rows by NameOfParameter; advanced inputs are the legacy Manual inputs, Settings and Constants; data come from the same databases; results carry the Excel-AI output codes.
  5. Structure that allows change. The core demand equations sit behind slots that the scenario input ModelForm can fill with other forms (D4); downstream modules (distribution, air pollution, transport co-benefits) talk to mitigation through declared interfaces.
  6. Documents from one source. qmd for people, generated Word copies, md for guides; the equation list in one source file for both of its versions.

3. Folder structure

3.1 Principles

  1. Keep what is clean. The top level of coded/ stays as it is: cpat_model/ (the model), cpat_shiny/ (the app), cpat_testing/ (tests), cpat_documentation/ (documents), and the entry points and configuration files. Only NORMS.md is added at the top.
  2. The package reads like the model. Inside cpat_model/, one subpackage per block of Excel-AI, named for what it computes, and one file, mitigation/chain.py, that lists the blocks in the order they run. A reader learns the model by reading chain.py, then each block in turn.
  3. Shared machinery in one place (core/), the switchable equation forms in another (forms/), so model blocks hold only equations.
  4. Inputs and data at the edge. Only inputs/ reads scenario files and only data/ reads databases; model code receives arrays.
  5. Documents in cpat_documentation/, one subfolder per kind (project, equations, developer, user), with qmd sources and generated Word copies.
  6. No working files in the core folders (NORMS 2.2): kept comparison scripts in cpat_testing/compare/, run outputs in coded/outputs/ (git-ignored).

4. How a run works

4.1 From inputs to results

4.2 Two passes, three stages (D1, D15: recommended options)

Excel-AI computes year by year with no circular reference: year t reads year t-1 and earlier (the GDP feedback reaches year t+1; power demand reads last year’s electricity price; capacity, vintages and vehicle stocks are recursions on t-1), and its only look-aheads read exogenous paths (the levelised variable cost of power over [t, 2041], built from prices and policies; next year’s manual capacity input). Policy scenarios also read scenario-1 values: stored ones (sheet BaselineCO2: CO2 by ETS sector, the calibration values in the GHG inventory year) and same-year ones (.ref, which reach the model only through the fiscal space and so GDP of t+1). Coded CPAT therefore runs the baseline first, then each policy scenario in turn (any number of scenarios; D15), each run in three stages:

Stage What Excel-AI blocks
Prepare (all years at once; nothing here depends on a quantity of the model) Years, CPI and deflator indices, baseline GDP growth, income factor, shock path; policy paths (carbon tax, ETS, feebates, excises, subsidy reform, methane fee, Pigouvian components from the module values); international prices and the retail-price chain before and after policies; power cost paths incl. the levelised variable cost 0, 1, 2, power costs of 3
Year loop (t = base year + 1 … last year; each block reads year t and earlier) GDP level of t (from the effect of t-1); road engineer model; fuel demand by sector and fuel (the core-equation slot); residential leakage and the exempt split; power demand, dispatch, retirement, investment, electricity prices; energy totals; revenues; CO2 (and the ETS check); other GHGs and methane; local air pollutants; air-pollution and transport co-benefit modules for year t; GDP effect of t 16 (level), 5b, 5-8, 6b, 3 (quantities), 11, 12, 13, 14, 15, modules, 16
Finish (all years) Carbon-pricing indicators; inputs from the modules (modelled concentration, per-litre externalities); welfare, externalities, subsidies, efficient prices; exports to distribution 17, 17b, 18, 19

Outside the passes: the ETS goal seek (iterates whole runs until emissions meet the cap; run only on request, root NORMS 5c) and the range-anxiety fit (offline, stored as data), as in Excel-AI.

Every function works on all countries at once (an array dimension); scenarios run one after another, and their results are joined along a scenario dimension.

4.3 One year of the loop (the chain)

mitigation/chain.py holds exactly this list, so the order is written once.

4.4 Switchable core equations (D4)

Each form provides a function for every slot with the same signature; a block calls the slot, never a form directly. Only CPAT is built now; the others must not change its numbers (section 7).

4.5 Modules and their interfaces

Module Reads from mitigation Returns to mitigation Used in mitigation Placeholder behaviour now
Distribution Section 19a (about 29 rows, both scenario groups) nothing - Built (to be moved onto the new structure)
Air pollution Section 15 (aps.<pollutant>.<module sector>), energy use of power and residential by fuel, CO2, GDP, population air.vpm (value of averted PM2.5, by year), concentration coefficients by module sector and pollutant Pigouvian tax (prepare stage: exogenous, I151) and welfare, subsidies, efficient prices (finish) Returns Excel-AI’s typed values (FromAirPollution: Egypt from the legacy 465 run; 0 elsewhere, I106) in prepare; its year-t step records its inputs and computes nothing
Transport co-benefits Section 5b (road fuel use by class, fuel economy, vehicle-km by class, road share) tran.acc.km, tran.con.km, tran.rdm.km (cost per vehicle-km) Pigouvian tax (prepare) and road welfare (finish) As air pollution, from FromTransportCB

Why the module values enter in prepare, not in the loop: in Excel-AI the Pigouvian tax uses them, the tax enters the power policy cost and so the forward-looking levelised cost; a damage that depended on this year’s emissions would make the model circular (issue I151). Each placeholder module therefore has two hooks: prepare (exogenous values, used now) and step(t) (the live module, later). If a live module’s damages are to feed back into prices, that needs an outer iteration or a one-year lag: a decision for when the module is built.

7. Switchable equation forms

The behavioural core of CPAT is a small number of equations: fuel demand by sector and fuel, electricity demand, power supply (dispatch and investment) and road transport. Excel-AI implements each as a named LAMBDA (FUELUSE and AEEIFACTOR for fuel demand, DEMANDMULT for electricity, DISPATCH, LOGITW, FIRSTROUND, CHEAPFILL, LEVELISED for power, ROADSWITCH, DEMROAD, OWNDEM, GOMPTGT for road transport).

The switch is a scenario input (D4). A new input ModelForm is added at the end of the MTInputs rows (below the last legacy row, in the block of prototype additions, root NORMS section 4), the same in Excel-AI’s ScenarioDefinition and in Coded CPAT’s scenario sets, one value per scenario. In Excel-AI the LAMBDA of each core equation reads it; in Python the block calls a slot in cpat_model/forms/, and ModelForm decides which implementation fills it.

The existing selectors stay as they are. The engineer-or-elasticity selectors of power and road transport (TrModel, and the power model choice) are unchanged and are not overridden by ModelForm; power always uses the engineer model. ModelForm chooses the form of the demand equations:

ModelForm Fuel and electricity demand Status
CPAT (default) CPAT constant elasticities (Excel-AI FUELUSE, DEMANDMULT) Built first: replicates Excel-AI
CPAT partial adjustment Partial adjustment towards the CPAT long-run level (issue I62) Later
CES partial adjustment CES demand for energy services with partial adjustment, taking the CES-compatible price of each service Later
CDPM-FTT CDPM (SISEPUEDE)-like stock model with FTT-like technology diffusion Later

“Simple-CPAT” and “standard-CPAT” of the original request are then the CPAT form with the elasticity or engineer selectors of road transport (and, if it is ever built, of power).

Rules: every implementation of a slot has the same signature (year t and t-1 values in, year t values out); a new form never changes the numbers of CPAT; a form that needs new parameters takes them from the advanced inputs, with defaults that leave CPAT unchanged; the row is added to Excel-AI and Python in the same release.

Structure and computation

D1. Order of computation: year by year, or module by module? (decided: see the table)

  • A. Year by year, all modules within the year (recommended). Three stages: prepare (all years at once, for everything without feedback: policy paths, international prices, deflators, exogenous drivers, base-year calibration), the year loop (for t = base year + 1 … last year, every block of mitigation, then air pollution and transport co-benefits, for year t; GDP of year t feeds year t+1), finish (all-year results, welfare, indicators; distribution in its analysis year). This is how Excel-AI computes (years across, each year reads the year before; GDP feedback one year later, NORMS 5c), so the numbers match by construction, and later modules with feedback (Pigouvian taxes from air-pollution damages, endogenous transport) fit without restructuring.
  • B. Module by module, each over all years at once (vectorised in time). Simpler for blocks without feedback, but the GDP feedback and the lagged price terms force iterations over the whole model until convergence; harder to match Excel-AI exactly.
  • C. Hybrid by module: modules without feedback over all years, the rest year by year. Two styles in one code base; less readable.

D2. How quantities are held in the code (decided: see the table)

  • A. Labelled arrays, xarray (recommended). Each quantity is an array with named dimensions (country, scenario, year, fuel, sector, …). Equations read like the equation list (ener = ener_prev * (atp / atp_prev) ** eps_u), broadcasting by name; many countries and scenarios cost nothing extra. One added dependency.
  • B. pandas DataFrames with a MultiIndex (today’s coded/): familiar, but index alignment and year columns as strings make equations long.
  • C. numpy arrays with axis conventions: fastest, least readable.

D3. Variable names in the code (decided: see the table)

  • A. CPAT code stems (recommended): ener, atp, ctx, with _prev, _ref, _chg suffixes; a generated variable registry (from the codes map) gives description, unit, dimensions and Greek symbol. Matches Excel-AI and the outputs one to one; the codes are short but documented in every docstring.
  • B. Descriptive English names (fuel_use, after_tax_price) with the code as metadata: easier for a newcomer, but two vocabularies to keep aligned.

D4. The switch between equation forms (decided: see the table)

  • A. One global setting model_form, mapped to a form for each core-equation slot (recommended). Slots: fuel demand, electricity demand, power supply, road transport, service price (CES-compatible price). Forms: simple_cpat (elasticity equations for every sector, power and road included), standard_cpat (Excel-AI: engineering power and road models on; default), cpat_partial_adjustment, ces_partial_adjustment, cdpm_ftt (SISEPUEDE-like stock model plus FTT-like technology diffusion). Each form is a function with the same signature, registered in cpat_model/forms/, as Excel-AI’s LAMBDAs. Only standard_cpat (and the switches Excel-AI already has, e.g. TrModel) is built now.
  • B. As A, plus an override per slot or per sector (e.g. CES in buildings only). Can be added later without changing A.
  • Question: should the scenario inputs that already switch models in Excel-AI and legacy (road transport TrModel, power) stay per-scenario inputs, with model_form only setting their defaults? (recommended: yes)

D5. Input files (decided: see the table)

  • A. Scenario set: one table (xlsx or CSV), rows = the legacy MTInputs rows in order (NameOfParameter), columns = scenarios, plus a row per scenario for the country (or “all”); Excel-AI’s ScenarioDefinition pastes into it. Advanced inputs: one workbook with one tab per kind (time series by year, tables by fuel and sector, settings), defaults from Excel-AI Settings, Manual inputs and Constants. The Shiny app writes the same structures in memory.
  • B. YAML/JSON scenario files (one per scenario). Readable for programmers, but not the MTInputs form people use.
  • Question: can one scenario set mix countries (scenario x country pairs), or is a scenario always “these inputs for every listed country”? (recommended: inputs per scenario, applied to a list of countries; country-specific values through the advanced inputs)

12. Excel-AI choices to flag

The overriding norm is to replicate Excel-AI. These choices are replicated as they are, but they are unusual enough that the user should know of them before the build; each is already in the register or proposed for it.

  1. Stored scenario-1 values. Policy scenarios read baseline values stored on sheet BaselineCO2 and refreshed by the build (CO2 by ETS sector for the ETS cap and price estimate; the CO2 calibration factor and the energy-methane calibration in the GHG inventory year, 2024, which is after the base year). In Excel the results therefore depend on values stored by the last build, not on the current inputs. Coded CPAT computes them in its baseline pass (D15); the two agree only while Excel-AI’s stored values are current, which the comparison checks.
  2. Scenario inputs that act as global settings. Some inputs are read from the scenario-1 column for every scenario (BiomassLeakage, BiomassNormal, the cooking-exemption inputs, cookstove efficiencies). In Coded CPAT they become run settings (D16), with a check that every scenario column agrees.
  3. The road engineer model runs in every scenario whatever TrModel (issue I100); its outputs feed the transport co-benefit interface even when the elasticity form drives fuel use.
  4. Module values typed for Egypt only. The air-pollution and transport co-benefit values (FromAirPollution, FromTransportCB) are typed from the legacy 465 run for Egypt; every other country reads 0 (I106), so Pigouvian taxes and those welfare terms are zero outside Egypt.
  5. Pigouvian taxes by proxy (I151): marginal air-pollution damages use base-year fuel-use weights and typed values, so they do not respond to the scenario; this keeps the model acyclic (the tax enters the forward-looking power cost) and is the reason the placeholder modules feed the model in the prepare stage.
  6. Fuel demand has no partial adjustment (I62): the full response to a price change happens in the year of the change. The cpat_partial_adjustment form addresses this later.
  7. Investment need extrapolates required generation as Req(t)²/Req(t−1) instead of reading next year (L67 fix), and the levelised variable cost of power looks forward to 2041: both are exogenous, so they sit in the prepare stage.
  8. ETS price by goal seek. The ETS permit price is found by an outer iteration over whole runs (run only on request); between runs it is a stored override row per scenario. Coded CPAT keeps the override as an advanced input and offers the iteration as a separate function.

12b. Apparent errors in the methodology documentation

Registered as documentation bugs DOC1-DOC20 (new code DOC, root NORMS section 0; excel_ai/core/BUGS.md section 3). Found while extracting the notation (full list: ../equations/reference/notation_from_methodology.md section 4). They do not change Coded CPAT, which follows Excel-AI, but the methodology should be corrected:

  • No in-model GDP equation: neither the multipliers chapter nor the mitigation chapter gives the GDP feedback; the equation list takes it from Excel-AI.
  • Undefined symbols: \(\epsilon_G\) in both power-demand equations (presumably \(\epsilon_Y\)); \(tex\) in Appendix C.
  • Markup sign: \(mu^T = gnc^{av} + tmc - hrp\) is then added to the price; to reproduce historical prices it must be \(hrp - gnc^{av} - tmc\).
  • Storage: the derivative of \(sst = 9v^2\) is written \(18v^2\) (should be \(18v\)); the long-term storage table does not match its formula.
  • Welfare: \(ddw\) uses \(nc\) for \(ncp\), and the text calls half the difference of the taxes their average.
  • Supply price: producer subsidies added in Appendix C, subtracted in the main text; base-year window 2019-2021 in one place, 2018-2022 in another.
  • Overloaded letters: \(g\) (sector group, generation, growth rate, consumption category, PIT gain), \(\gamma\) (six meanings), \(E\), \(p\)/\(P\), \(j\), \(i\); electricity coded ecy in mitigation and ely in distribution. The equation list fixes one meaning per letter within each part (its symbol appendix).
